# 第一册贯穿案例：TurtleMission单乌龟自主任务系统

## 1. 教学定位

第一册使用一个持续演进的turtlesim工程，而不是一组彼此无关的小实验。总案例命名为“TurtleMission单乌龟自主任务系统”，用于说明ROS如何组织简化智能机器人软件。

统一闭环为：

`任务目标 → 位姿感知 → 误差或规则决策 → 速度执行 → 新位姿反馈`

案例保持单乌龟、纯仿真，不引入真实机器人、多乌龟追踪、编队、复杂状态机、TF数学与深入诊断、SLAM、导航或MoveIt。

## 2. 递进版本

### V1 TurtleGoal：自主到达目标点

任务：接收二维目标点，订阅`/turtle1/pose`，计算距离和方向误差，发布`/turtle1/cmd_vel`，在允许误差内停止。

主要知识：节点、计算图、Topic、Message、Publisher、Subscriber、Timer、Callback、Python面向对象、简单比例控制、日志和ROS1/ROS2实现对照。

最低可观察证据：目标点、实际轨迹、距离误差、到达判定和停止后的零速度指令。

### V2 TurtleGuard：虚拟围栏与安全避界

任务：根据位姿和边界距离决定正常运行、减速、转向或停止，防止乌龟进入危险区域。

主要知识：Parameter、YAML、参数校验、多条件规则、节点职责、QoS入门、告警日志和异常输入处理。

建议参数：`safe_margin`、`warning_margin`、`max_linear_speed`、`max_angular_speed`。

最低可观察证据：边界距离、安全模式、速度限制前后值、触发告警和恢复正常的条件。

### V3 TurtlePainter：可反馈、可取消的轨迹绘制任务

任务：接收图形、尺寸、起点和速度等任务目标，沿路径段绘图，持续反馈进度，支持取消并安全停止。

主要知识：Service与Action的适用边界、自定义接口、Goal/Feedback/Result、异步调用、执行器、回调组、多线程入门、任务取消、接口生成和CMake。

建议目标字段：`shape_name`、`size`、`start_x`、`start_y`、`speed`。

建议反馈字段：`progress`、`current_segment`、`remaining_distance`。

建议结果字段：`success`、`total_time`、`position_error`、`message`。

使用路径段顺序完成任务，但不在第一册展开正式状态机理论。

### V4 TurtleMission：参数化自主任务系统

任务：从YAML加载任务，综合目标到达、边界保护和轨迹绘制，支持统一启动、运行记录、任务取消、异常处理和结果评价。

建议节点：

| 节点 | 职责 |
|---|---|
| `pose_monitor` | 订阅、校验和发布所需位姿状态 |
| `goal_controller` | 根据目标和反馈计算速度指令 |
| `safety_guard` | 监测边界并限制危险指令 |
| `mission_server` | 接收、执行、反馈和取消任务 |
| `performance_logger` | 记录误差、时间、事件和运行结果 |

主要知识：Workspace、Package、Launch、YAML、Remapping、Namespace入门、自定义接口、日志、rosbag、计算图、故障定位、Git、README和ROS1/ROS2迁移分析。

## 3. 章节映射建议

| 章 | 核心内容 | 案例增量 |
|---|---|---|
| 第1章 | 智能机器人、ROS与TurtleMission总任务 | 讲解任务目标、功能架构、闭环与四阶段路线；不安装、不运行 |
| 第2章 | Linux与Ubuntu基础 | 准备开发环境，不实施完整案例 |
| 第3章 | ROS环境、turtlesim初体验、工作空间与功能包 | 安装完成后首次启动和手动控制turtlesim，并建立统一工程；不实施完整案例 |
| 第4章 | 节点、计算图与ROS工具 | 设计节点职责，不实施完整案例 |
| 第5章 | Topic、Message与位姿感知 | 完成案例所需感知基础，不实施完整案例 |
| 第6章 | 发布控制与反馈闭环 | 完成TurtleGoal |
| 第7章 | Parameter、YAML与Service | 完成TurtleGuard |
| 第8章 | Action与异步执行 | 完成TurtlePainter |
| 第9章 | Launch、记录、调试与系统集成 | 完成TurtleMission |
| 第10章 | ROS1/ROS2迁移、测试与总结 | 对四个案例迁移、测试和复盘，不新增案例 |

第1章只允许用任务架构图说明TurtleMission，不得出现启动命令、运行结果或要求学生操作turtlesim。turtlesim的首次启动、手动控制和运行观察必须放在第3章ROS安装完成之后。第1至5章可以逐步观察turtlesim、初始化工程和开发基础组件，但不得提前呈现尚无知识支撑的完整案例。第6至9章每章只承担一个新的阶段案例，并复用此前代码。第10章不得以“综合案例”名义重复编写TurtleMission。

## 4. 统一工程规则

- 四个版本使用同一仓库和同一功能包体系，通过tag或里程碑目录保留可复现版本。
- 每章先复现上一版本，再增加一个主要能力，避免一次重写整个系统。
- ROS2 Humble与`rclpy`是主实现；关键案例提供ROS1 Noetic与`rospy`迁移对照。
- 每个关键实现给出环境、命令、预期现象、典型故障和验证状态。
- 控制算法保持基础程度，服务ROS概念教学，不把第一册写成控制理论、路径规划或导航教材。

## 5. 故障注入清单

至少覆盖：

- Topic名称错误或Remapping错误；
- 消息类型或自定义接口不匹配；
- 节点、参数文件或Action Server未启动；
- YAML字段缺失、类型错误或数值越界；
- 控制频率过低、速度过大或停止条件不合理；
- 目标点超出有效区域；
- Action不能取消或取消后未发送零速度；
- 节点异常退出后系统未进入安全状态；
- ROS1与ROS2命令、构建系统或接口导入混用。

## 6. 期末项目最低验收

学生须提交：代码仓库、环境说明、节点与接口图、参数文件、启动方式、测试用例、运行记录、故障分析和项目报告。

系统至少满足：

1. 接收并校验任务目标；
2. 获取位姿并形成闭环控制；
3. 执行目标点或轨迹任务；
4. 提供安全边界约束；
5. 发布任务反馈并支持安全取消；
6. 处理至少三类异常；
7. 记录运行时间、轨迹或误差证据；
8. 使用ROS工具完成一次有证据的故障诊断；
9. 对ROS1与ROS2实现差异作迁移分析。

不得仅以“乌龟画出了图形”作为验收结论；必须同时评价接口正确性、停止安全性、误差、可复现性和诊断证据。
