# ROS 与软件版本策略

## 总原则

教材必须把“长期有效的系统概念”和“随发行版变化的实现细节”分开。不得仅凭记忆给出安装命令、包名、API或兼容关系；易变化内容在定稿前查阅官方一手资料。

## 立项版本矩阵

每册正式写作前建立并批准以下矩阵：

| 项目 | 主教学环境 | 对照环境 | 验证状态 |
|---|---|---|---|
| Ubuntu版本 | 22.04（ROS2） | 20.04（ROS1） | 环境待验证 |
| ROS1发行版 | Noetic | — | 代码必须验证可运行 |
| ROS2发行版 | Humble | Humble（同一基线） | 逐章验证 |
| Python API | rclpy | rospy | 关键案例均提供Python版本 |
| 构建系统 | colcon/ament | catkin | 待逐章验证 |
| Gazebo产品与版本 | Fortress（Humble官方组合） | Noetic兼容环境待明确 | 插件待验证 |
| MoveIt版本 | MoveIt 2 | MoveIt/ROS1迁移提示 | 待逐章验证 |
| 导航框架 | Nav2 | ROS1 Navigation Stack | 待逐章验证 |

没有批准版本矩阵时，可以规划概念和目录，但不得把具体命令标记为“已验证”。

Humble为本项目已批准的主教学与对照验证发行版，不另设第二个ROS2教学发行版。当前教材只声明Humble验证；未来长期支持发行版在再版时建立新矩阵并重新验证。除非有CI或逐发行版运行记录，不得声明兼容多个ROS2发行版。

## ROS1与ROS2的组织方式

1. 先讲共同问题和共同概念，不先按版本分成两套课程。
2. 每章选择一个最小共同案例，分别展示必要的ROS1和ROS2实现。
3. 对照内容统一使用五类标签：
   - `共同概念`
   - `ROS1实现`
   - `ROS2实现`
   - `迁移提示`
   - `版本警告`
4. 对照重点包括：发现机制、中间件、构建系统、工作空间、节点API、参数、Launch、QoS、工具和包管理。
5. ROS1专有内容不得暗示为ROS2通用做法；ROS2特性不得反向套用到ROS1。

## 验证记录

每个代码或实验至少记录：

- 操作系统与架构；
- ROS发行版；
- 仓库提交或教材代码版本；
- 依赖安装方式；
- 执行命令；
- 预期输出或证据；
- 验证日期；
- 验证范围：仿真、实物或仅静态审查。

## 长期维护

- 把易变化的安装说明集中维护，章节正文优先解释稳定概念。
- 每次再版复核官方支持状态、包名、API和兼容矩阵。
- 保留旧环境分支，不静默改写已出版代码。
- 对无法继续复现的内容标注历史环境和替代路径。
